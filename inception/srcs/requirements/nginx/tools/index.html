Docker, explained

A way to package an application together with everything it needs to run, so it behaves the same on your laptop, your teammate's laptop, and a server somewhere you've never seen.

01The problem it solves

Software rarely fails because the code is wrong. It fails because the machine running it is slightly different — a missing library, a different OS version, an environment variable nobody documented. Developers call this "works on my machine."

Docker's answer is to stop installing software directly onto a computer, and instead package the software with its entire environment — OS files, runtime, dependencies, configuration — into one unit that runs identically anywhere Docker is installed.

02Images and containers

These two words get used interchangeably, but they mean different things.

image

A frozen snapshot: the filesystem, dependencies, and instructions needed to run something. It doesn't do anything by itself — think of it as a saved recipe.

container

A running instance of an image. The image is the recipe; the container is the dish, actually cooking, with a process running inside it.

One image can spin up many containers, each isolated from the others, each with its own filesystem and process space, all sharing the same underlying image.

03Layers, and why they're fast

An image is built in layers — one on top of another, as shown above. Each instruction in a Dockerfile (install this, copy that) adds a new layer. Docker caches layers, so if you change one line near the end of a Dockerfile, only that layer and the ones after it need to rebuild. Everything below is reused.

This is also why images are small to distribute over a network: if two images share a base layer, that layer is only stored once.

04A minimal Dockerfile

A Dockerfile is the recipe: plain-text instructions describing how to build an image, top to bottom. 

# start from a base image
FROM node:20-alpine

# copy your app in
WORKDIR /app
COPY . .

# install dependencies
RUN npm install

# what to run when the container starts
CMD ["node", "server.js"]
$ docker build -t my-app .
# turns the Dockerfile into an image

$ docker run -p 3000:3000 my-app
# starts a container from that image

05Isolation, without a full virtual machine

Each container thinks it has its own filesystem, network, and process tree — but unlike a virtual machine, it doesn't carry a whole separate operating system. Containers share the host machine's kernel and stay lightweight, which is why you can run many of them side by side without much overhead.

06Running several containers together

Most real applications need more than one container: a web server, a database, maybe a cache — each isolated, but able to talk to each other. Docker Compose lets you describe that whole setup in one file, and bring it all up with one command instead of running each container by hand. 

# docker-compose.yml
services:
  web:
    build: ./web
    ports:
      - "80:80"
  database:
    image: postgres:16
$ docker compose up
# builds and starts every service defined above
